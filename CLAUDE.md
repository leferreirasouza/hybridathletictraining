# Hybrid Athletics — Claude Code Reference

## Project overview

A multi-tenant HYROX coaching platform. Coaches manage athletes; athletes self-serve training plans and session logs. Built on React + TypeScript (Vite), Supabase (Postgres + Edge Functions), shadcn/ui, Recharts.

Live app managed by Lovable (project ID `32016a2e-7fa6-4e0d-9b0a-1626d38df80c`). GitHub repo: `leferreirasouza/hybridathletictraining`.

## CRITICAL: How deployment works

**Git push alone does NOT deploy Supabase Edge Functions — and "Lovable says it deployed" is not sufficient proof either.**

- **Database migrations**: Apply via Lovable MCP tool (`mcp__Lovable__query_database`) or paste SQL into Lovable's chat. Migrations in `supabase/migrations/` are committed for record-keeping only. A separate `drizzle/migrations/` tree also exists (added 2026-10, `drizzle.config.ts`) for admin-RPC-style migrations written directly in Lovable chat sessions — same live DB, two migration folders, neither is authoritative on its own; always re-verify against the live schema (`information_schema`, `pg_policies`), not either folder.
- **Edge Functions**: Must be pasted into Lovable's Build-mode chat. Lovable's agent deploys them. The Edge Functions dashboard timestamp is unreliable — only functional verification (query the DB for expected side effects) confirms a deploy is live.
- **Frontend/UI**: Lovable auto-syncs from the `main` branch into its *editor*, but **the live site only changes on a republish** (confirmed 2026-10-23: a merged privacy-policy fix sat unpublished until Lovable ran `publish`). After every frontend merge, ask Lovable to republish and confirm the production domain renders.
- **Edge functions from `main`** (2026-10-25): once a PR is merged and Lovable has synced, asking Lovable to "redeploy functions X, Y exactly as in the repo, no code changes" works — no need to paste file contents. Remember a changed `_shared/` module only takes effect in functions that are redeployed (grep for importers). Lovable regenerates `src/integrations/supabase/types.ts` on such passes — check `get_diff`.
- **Branch strategy**: Claude Code remote sessions auto-create a branch (`claude/access-github-project-a0Qer`). Work there, open a PR, merge to main when done. Do not accumulate long-lived feature branches. When the branch's last PR was merged, restart it from `origin/main` before starting new work — `main` regularly moves ahead of this branch via direct Lovable-chat sessions the user runs without Claude Code. **Confirmed again 2026-10-12:** 19 direct-Lovable-chat commits landed between 2026-10-01 and 2026-10-12 with zero Claude Code involvement (Stripe billing scaffolding, `strava-subscribe`, the admin Athletes&Strava tab, opening plan-suggestion accept/dismiss to athletes, Week Builder, a full PT-BR localization pass). Always run a fresh `list_edits`/`get_diff` review before assuming you know the current state of `main`.
- **Verified incident (2026-09-21):** the 2026-07-02 migration (`strava_sync_and_token_encryption.sql`) was reported deployed but **silently never applied to the live database for ~2.5 months**. Dependent Edge Functions (`strava-webhook`, `garmin-webhook`, `garmin-oauth`) ran against tables/columns that didn't exist that whole time. It was only caught when someone re-queried `information_schema.tables` directly. **Lesson: after any migration or function "deploy," independently re-verify against the live DB/behavior — don't trust the deploy confirmation message alone**, whether it comes from Lovable's agent or from Claude.
- **Second instance of the same failure class, found 2026-10-12:** `generate-plan`'s `periodization_adjustments` insert ran with zero error-checking since the feature shipped — if it had been failing every time, nothing would have shown it. The table had 0 rows "ever" and there was no way to tell whether that meant "working as designed, conditions never triggered it" or "silently broken." Fixed (now logs on insert failure) but **still functionally unverified** — nobody has watched it actually write a row. Treat "0 rows" claims about any table fed by an unchecked `.insert()` with suspicion until you've grepped for `{ error }` handling on that specific call.

## Key shared modules (all in `supabase/functions/_shared/`)

- `paceZones.ts` — Daniels VDOT: `estimateVDOT()`, `paceZonesFromVDOT()`, `decomposeHyroxTarget()`. Injected into prompt as "COMPUTED PACE ZONES (do not invent your own)."
- `phaseModel.ts` — Periodization: `buildPhaseSchedule(planWeeks, experience)` → base/build/peak/taper per-week table injected into prompt.
- `sessionSlots.ts` — Slot allocation: `assignWeeklySlots()` → deterministic run/strength/mobility_technique counts per week. `validateSlotCompliance()` → post-gen check writing to `periodization_adjustments` (adjustment_type `slot_mismatch`).
- `interferenceRules.ts` — `detectInterferenceConflicts()` (Hickson same-day/adjacent-day flagging, writes adjustment_type `interference_spacing`), `tsbAdjustmentFactor(tsb)` (fresh/neutral/fatigued/high_risk bands → intensity/volume caps, writes adjustment_type `tsb_intensity_reduction`). **Confirmed 2026-10-12: this module's output IS wired into `generate-plan`'s post-generation insert into `periodization_adjustments`** (not dormant/unwired as previously suspected) — see the generate-plan entry below for why it may still show 0 rows regardless.
- `runVolumeProgression.ts` — `buildRunVolumePlan()`: deterministic weekly running-volume ramp from the athlete's reported current km/week, respecting the 10%-rule week-over-week (`baseline * 1.1^(week-1)`) and an absolute 2.75x ceiling, scaled by `phaseModel.ts`'s per-week `volumeMultiplier`. Injected into `generate-plan`'s prompt as the authoritative per-week/per-slot km source of truth. Extended (2026-09) with a `week1CapKm` guardrail that clamps a self-reported baseline to 1.10x the athlete's *verified* trailing 4-week average (sourced from `recentTraining.ts`), plus return-from-layoff easing when no recent runs are detected. The wizard's `RunDaysCountStep.tsx` preview math must stay aligned to this exact formula — they drifted once already; re-check both sides if either changes.
- `recentTraining.ts` — 8-week trailing training summary from `completed_sessions` (weekly run km, discipline hours, avg pace/HR, days since last run, layoff detection at ≥14 days). **Deliberately duplicated** between here and the client copy at `src/lib/recentTraining.ts` (one runs server-side in Deno, one client-side) — kept aligned only by a code comment plus an automated parity test added 2026-09-30 (`src/test/recentTraining.parity.test.ts`). This is the same failure class that caused the `session_trimp()` bug below; if you touch one copy, touch both and re-run the test. **(2026-10-25)** The parity test had been failing to even load since Lovable changed `src/integrations/supabase/client.ts` to throw without `VITE_SUPABASE_URL` — the drift guard was silently down; fixed with a `vi.mock` of the client. Both copies now read `data_flags`: `distance_estimated`/`race` runs still count as km but are excluded from average pace, `hr_artifact` excluded from average HR.
- `stravaMap.ts` — `mapStravaDiscipline()` (sport_type/type → discipline, with a HYROX-name-hint regex fallback for generic "Workout"/HIIT types), `matchStravaActivity()`/`ingestStravaActivity()`: the shared matching engine used by both `strava-webhook` and `strava-sync`. Dedups against Garmin-sourced completions within a 10-minute window, picks the closest-duration planned-session candidate (not just first same-date match), only enriches NULL fields on existing completions (never overwrites manual data), falls back to an unplanned completion so history/load still sees the work. **(2026-10-25)** Now also dedups **Strava↔Strava**: before anything else, a recording overlapping ≥50% of the shorter of an already-linked recording (both ≥5 min, ±36h search) joins that completion and sets `strava_activities.duplicate_of` instead of creating a second one — watch + ROXFIT race import, watch + Peloton, Runna-inside-a-race had been double-counting load (7 real clusters found). Rows carry `data_flags` from `activityQuality.ts`; a HYROX race import overrides discipline (→ `hyrox_station`) and duration (→ official elapsed time) only on Strava-sourced completions. `ingestStravaActivity()` takes the athlete's `profiles.max_hr` (read once per batch in `strava-sync`).
- `activityQuality.ts` — **(new, 2026-10-25, hand-coded)** Import-free, so vitest loads the same file (`src/test/activityQuality.test.ts`). Decides what imported data is trusted: `isHyroxRaceImport()` (`external_id ^roxfit-hyrox-` or name `HYROX - City - H:MM:SS`), `isHyroxEffort()` (race imports, plus Run-type activities named hyrox/simulad ≥40 min → `hyrox_station`, not run km), `effectiveDurationSec()` (race imports use `elapsed_time` = official time; `moving_time` drops station work), `activityFlags()` → `race` (workout_type 1/11 or race import), `distance_estimated` (trainer/virtual/race import), `manual_entry`, `hr_artifact` (avg > athlete max, < 40, or > max), `max_hr_artifact` (max > athlete max + 10; 220/200 ceilings when unknown), and `isSameEffort()` for the dedup above. `scripts/backfill-activity-quality-2026-10-25.sql` mirrors these rules for stored rows — verified identical to the TS over all 247 live activities (md5 of discipline/duration/flags per row). **Backfill applied 2026-10-25** after owner review of the dry-run: 7 duplicate clusters merged (8 completions removed), 12 HYROX efforts → `hyrox_station`, 5 race durations → official time, 8-week run km 213.5 → 154.3, latest CTL/ATL/TSB 58.9/56.4/6.8 → 56.1/48.7/12.8. Verified afterwards: trigger re-enabled, every `duplicate_of` row shares its survivor's completion, no HYROX-named `run` completions left, one completion per race. New code verified live the same day (a fired `strava-sync` re-fetched the two description-less ROXFIT races and stored them with the new classification).
- `roxfitParse.ts` / `roxfitRaceResult.ts` / `raceDecomposition.ts` — **(new, 2026-10-25, hand-coded)** Automatic HYROX race results. ROXFIT race imports carry the official result in their Strava description (division, overall/AG rank, 8 runs, 8 stations by name, Roxzone). `parseRoxfitDescription()` (pure) maps stations by name, takes the official time from the activity name (`elapsed_time` fallback) and rejects anything without all 17 splits or whose splits miss the total by >10 s; `normalizeDivision()` folds "Mixed Doubles"/"Doubles Mixed" into one `division_key`. `upsertRoxfitRaceResult()` (called from `ingestStravaActivity()`, plus a ≤10/run catch-up in `strava-sync` over stored imports) is idempotent on `(athlete_id, strava_activity_id)`; a same-day manual entry within 5 s only gains missing fields, a same-day `goal` row (written by `generate-plan`) becomes the official result; never throws. `decomposeRace()` (pure, imported by both `RaceResults.tsx` and `hyrox-ai-coach` from the same file) compares only within one `division_key`, never relay, only full-split races: total/running/stations/Roxzone deltas vs previous and vs division best, biggest station gain/loss, run decay (runs 5–8 vs 1–4), slowest run vs median, dominant component, division PB. Tests: `src/test/roxfitRaces.test.ts` on the 6 real descriptions. **Verified live 2026-10-25** (after a fired `strava-sync`): 6 `roxfit` rows, every run+station+Roxzone sum within 5–7 s of the official time, division keys doubles_mixed ×3 / open_men / relay_mixed / doubles_men, and the owner's Washington DC `goal` row was converted into the result rather than duplicated (another athlete's same-day goal row untouched).
- `newSince.ts` — **(new, 2026-10-25)** `formatNewSince()` (pure, tested in `src/test/newSince.test.ts`): the AI coach's "NEW SINCE YOUR LAST CONVERSATION" block — Strava activities (non-duplicate, non-ignored, by `created_at`) and manual logs (by `completed_at`) after the athlete's previous chat message, max 8, with an instruction not to list them unprompted or invent any.
- `sessionLibrary.ts` — **(new, 2026-10-25, hand-coded)** `formatLibraryCatalogue()` (compact per-slot catalogue for the `generate-plan` prompt), `effectiveLibrary()` (org entry overrides a global one with the same code), `resolveLibraryCodes()` (case-insensitive code → `session_library.id`, counts unknown/missing). Pure, tested in `src/test/sessionLibrary.test.ts`.
- `readinessGates.ts` — **(new, 2026-10-25, hand-coded, inert until Garmin data exists)** `evaluateReadiness(days, today)` over merged daily `{sleepHours, hrvMs, restingHr}` (`mergeGarminDays()` prefers overnight HRV from `garmin_sleep`): `short_sleep` (2 consecutive nights < 6.5 h), `hrv_low` (7-day HRV below 60-day baseline mean − 1 SD; ≥14 baseline + ≥3 recent nights, only nights with ≥7 h sleep), `rhr_elevated` (3-day RHR ≥ prior 7-day + 5 bpm); single HRV/RHR values >40 % off the trailing 7-day mean dropped as artefacts; no data in the last 3 days → `insufficient_data`. Thresholds are exported constants taken from the owner's personal system — defaults, not validated cut-offs. Tested in `src/test/readinessGates.test.ts`.
- `maxHrEstimate.ts` — **(new, 2026-10-25, hand-coded)** Only 3/15 profiles had `max_hr`, so HR plausibility fell back to generic 220/200 ceilings for everyone else. `estimateMaxHr()` = 98th percentile (nearest rank) of plausible (120–220) session maxima over 365 days, ≥20 sessions, `max_hr_artifact` sessions excluded — on the owner's data it gives 197 (spikes 209/211 excluded; profile said 194, sessions repeatedly hit 196–199). `fetchAthleteMaxHr()` in `stravaMap.ts` now uses profile → estimate → null. `maxHrAdvice()` drives `src/components/dashboard/MaxHrCard.tsx`: suggest the estimate when unset, suggest raising when the data exceeds the profile by ≥3 bpm ("Keep" is remembered per value in localStorage), else ask to enter one. **Only a confirmed value is written to `profiles.max_hr`** — that is what `session_trimp()` reads, so the estimate never changes training load on its own. Tested in `src/test/maxHrEstimate.test.ts`.
- `tokenCrypto.ts` — `encryptToken()`/`decryptToken()` (AES-256-GCM via Web Crypto, `enc:v1:`-prefixed so legacy plaintext rows transition safely — `decryptToken()` returns non-prefixed values as-is) and `hashToken()` (HMAC-SHA256, non-secret lookup key, separate key from the encryption key). Used for all Garmin/Strava OAuth token storage. **`TOKEN_ENCRYPTION_KEY`/`TOKEN_LOOKUP_HMAC_KEY`/`STRAVA_WEBHOOK_VERIFY_TOKEN` were pasted as literal plaintext values into a Lovable chat message on 2026-07-02** — **still not rotated as of 2026-10-12, now 102+ days.** This is the single highest-priority open item in the whole project. Rotation requires the owner (no MCP tool can touch the Supabase secrets manager) — set new values in Project Settings → Edge Functions → Secrets (never paste into Lovable chat, which is the exact mistake being corrected), then re-run a re-encryption backfill against every `strava_connections`/`garmin_connections` row before the old key is discarded, or those connections break. **`scripts/rotate-token-encryption-keys.ts` (added 2026-10-12) is exactly this backfill, ready to run** — takes `OLD_TOKEN_ENCRYPTION_KEY`/`NEW_TOKEN_ENCRYPTION_KEY`/`NEW_TOKEN_LOOKUP_HMAC_KEY` as env vars, decrypts every row with the old key and re-encrypts with the new one before the secrets are flipped live; see its own header comment for the required sequencing. Distinct from `scripts/backfill-token-encryption.ts`, which only handles legacy plaintext rows, not a key rotation.
- `subscription.ts` — **(new, 2026-10, unwired)** `getStripeClient()`, `getAthleteTier(service, athleteId)` (reads `subscriptions.tier`/`status`, defaults to `"free"` if no row or status isn't active/trialing), `tierAtLeast(tier, required)`. Built for gating `generate-plan`/`hyrox-ai-coach` behind a paid tier — **confirmed 2026-10-12 that neither function calls it.** Nothing is gated. Needs a product decision (what's free vs paid) before wiring it in. **Draft wiring ready, 2026-10-12:** exact diffs for both functions, plus the open decisions (hard gate vs soft quota; whether to grandfather the 15 existing `auth.users` accounts, who currently all default to `"free"`; whether both functions should share one gate) are at `scripts/drafts/stripe-tier-gating-wiring.draft.md` — inert, not applied, by design (wrong file location for Supabase to deploy it).
- `stravaToken.ts` — `getValidStravaAccessToken()` (decrypt/refresh-if-near-expiry/re-encrypt), `findUserIdByStravaAthleteId()`. **Note:** as of mid-2026 `hyrox-ai-coach` had its own separate, independently-written token-refresh code path that bypassed this helper, read tokens without decrypting, and wrote refreshed tokens back in plaintext — silently reintroducing the exposure this module exists to prevent. ## Key edge functions (live, Lovable-managed)

- `generate-plan` — AI plan generation. Accepts optional `athleteId` + `organizationId` for coach-on-behalf-of-athlete flow, verified via `coach_athlete_assignments`. Uses `effectiveAthleteId` throughout (not raw `user.id`). Injects pace zones, phase table, slot table, run-volume table into prompt. Non-blocking `session_blocks` insert after `planned_sessions`. **Read in full 2026-10-12:** the "deterministic post-hoc safety net" section DOES call `detectInterferenceConflicts`, `tsbAdjustmentFactor`, and `validateSlotCompliance` on the freshly-inserted sessions and DOES attempt to insert any findings into `periodization_adjustments` — it is wired, not dormant. But: (1) the TSB branch only fires if `training_load_daily` already has a row for this athlete *before* the plan is generated — for a brand-new athlete's first plan (the common case, given 7 plans/15 profiles and TSB requires prior logged training) this is always null and the branch is skipped entirely; (2) the interference/slot-compliance checks only fire if the LLM actually violates constraints that are *also stated directly in its own prompt*, so a compliant model output produces nothing to insert; (3) until the 2026-10-12 fix noted above, the insert's result was never checked, so a DB-level failure would have been silent. Net: "0 rows ever" is consistent with either "working correctly, conditions just haven't coincided" or "was quietly broken" — **genuinely unverified; needs a deliberate test** (seed an athlete with a `training_load_daily` row showing TSB < -10, then generate a plan, then check for a `tsb_intensity_reduction` row).
- `hyrox-ai-coach` — Streaming chat with RAG (pgvector knowledge base). Hardened 2026-09-21: removed hard-coded per-athlete system prompts previously selected by matching the user's (editable) `full_name` — any user could rename themselves to obtain another athlete's personal AI context; replaced with a `coach_context` table. Also added request rate-limiting (30/hr) and message-length truncation, and removed the plaintext-token Strava bypass noted above. **Extended 2026-10-01** (direct Lovable chat, commit message "Deployed ungated coach prompt" — misleading name, read in full 2026-10-12: nothing was un-gated) to inject a `TRAINING LOAD (CTL/ATL/TSB + form band)` and `RACE HISTORY (PBs)` section into the system prompt, scoped correctly to the authenticated `userId` via the service-role client. Still not tier-gated (see `subscription.ts` above). **(2026-10-25)** The "RECENT COMPLETED SESSIONS (last 5)" block had been empty since it shipped — it selected a non-existent `completed_sessions.session_name` column; now joins `planned_sessions(session_name)`. Activity/rollup lines carry `data_flags` notes, duplicate recordings are skipped, indoor bike km is never summed and treadmill run km is reported separately. **(2026-10-25, WS2)** RACE HISTORY is now per division — it previously took the minimum time over every row, so a Mixed Relay (1:09) would have been reported as the PB next to Open Men (1:15) — plus the latest race's decomposition. **(2026-10-25, WS3) Chat persistence:** one `ai_threads` row per user (get-or-create) and **only the newest user turn** of each request is stored in `ai_messages` (assistant replies are not stored — owner decision). Before this, nothing ever wrote these tables, so the 30/hour limit had **never enforced**; it does now. The previous user message's timestamp drives the new-since block (`_shared/newSince.ts`); `AIChat.tsx` shows a matching "N new sessions since your last chat" line. Disclosed in `privacy.s1body` (en + pt-BR, `lastUpdated` → October 2026). Account deletion already cascades (`ai_threads.user_id → auth.users ON DELETE CASCADE`, `ai_messages.thread_id → ai_threads ON DELETE CASCADE`).
- **(2026-10-25, WS4)** `generate-plan` now loads approved `session_library` entries (global + the plan's org; the org id is UUID-checked before it is interpolated into the PostgREST `.or()` filter, since a global master_admin passes the membership check with any value), injects them as a `📚 SESSION LIBRARY` catalogue after the run-volume table, requires a `library_code` per session, and stores the resolved id in `planned_sessions.library_session_id`. Unknown/missing codes are logged and returned as `librarySessionsUnmatched` — deliberately **not** written to `periodization_adjustments` (that table feeds the Accept/Dismiss UI; a "missing code" row has nothing to accept). - `weekly-report` — AI commentary on weekly summaries.
- `compute-training-load` — Banister TRIMP + CTL/ATL/TSB EWMA computation (daily cron). `session_trimp()` was fixed 2026-09-21 after being found to return **0** whenever a session had both `resting_hr` and `rpe` NULL — true for essentially every Strava-synced session, which had silently zeroed out training-load data for the engine's entire real-world usage window. Now falls back to `COALESCE(resting_hr,60)`/`COALESCE(max_hr,190)` and an RPE- or duration-based estimate. All historical data was recomputed after the fix. **Also runs `proposeIfLowAdherence()`** (found 2026-10-12 while tracing why `periodization_adjustments` has 0 rows): a real, already-live suggestion rule — 2 consecutive completed weeks both under 70% planned-session adherence proposes a 20% volume cut on the athlete's next upcoming session, 14-day cooldown, `adjustment_type = "adherence_volume_reduction"`. Not documented anywhere before this note. **(2026-10-25, WS5)** Also runs `proposeIfNotReady()` — a fired readiness gate (above) with a hard/race_pace/max_effort session planned today or tomorrow raises one `readiness_downgrade` proposal (`source='readiness_check'`, one intensity step down via `downgradeIntensity()`, 3-day cooldown; silent for athletes without `garmin_dailies`/`garmin_sleep` rows, i.e. everyone until Garmin connects) — and `cancelStaleSuggestions()`, which sets `pending_coach` suggestions whose target session's date has passed to `cancelled`. - `strava-connect` / `strava-activities` — OAuth2 connect + activity-list proxy fetch. Tokens encrypted at rest. `strava-connect` now fires an async `strava-sync` backfill immediately after first token exchange.
- `strava-sync` — Historical backfill + resumable cron sync, sharing `_shared/stravaMap.ts` with the webhook. Two auth modes: user JWT (syncs caller) or `x-cron-secret` (loops all connected users). First run backfills 180 days; later runs resume from `last_sync_at` with a 6h overlap. Respects Strava rate-limit headers, 90s soft deadline with resumable cursoring, fetches full detail only for the most recent 30 activities per run. Confirmed live and working as of 2026-09-30 (210 rows in `strava_activities`).
- `strava-webhook` — Real-time Strava sync: GET handshake + POST event delivery, acks within Strava's 2s window, does activity-fetch/match/insert in the background via `EdgeRuntime.waitUntil`. Shares matching logic with `strava-sync` via `stravaMap.ts`, tolerates malformed bodies, checks `STRAVA_WEBHOOK_SUBSCRIPTION_ID`, and the deauth handler doesn't trust an unsigned `authorized:false` payload — it probes Strava's `/athlete` endpoint with the stored token and only deletes the connection on a confirmed 401.
- `strava-subscribe` — **(new, 2026-10)** `master_admin`-only (checked via `has_role` RPC against a service-role client, not just a frontend gate): GET lists the app's current Strava push subscription(s), POST registers `strava-webhook` as the callback (Strava client secret stays server-side, never returned to the caller), DELETE removes one. **Registered 2026-10-12** (per `list_edits`), but **whether Strava is actually delivering real-time events through it is still unconfirmed** — a real workout needs to be logged and checked against `strava_activities`/function logs before trusting this is live, not just that registration succeeded.
